## ① 업로드 계약 조항 (구현됨)

- 새 업로드는 「노래방 MR 제공 · 커버 허락」 동의가 필수다. 문구는 `shared/site-info.js`의 `KARAOKE_TERMS_TEXT`, 버전은 `KARAOKE_TERMS_VERSION`.
- 곡마다 동의한 약관 버전(`tracks.karaoke_terms`)과 시각(`tracks.karaoke_at`)을 저장한다. 마이그레이션 `0008_karaoke_consent.sql`.
- 조항 이전에 올라온 곡은 자동 적용하지 않는다. 창작자가 곡 수정 화면에서 따로 동의하면 포함된다 (`POST /api/uploads/:id/karaoke`). 한번 기록된 동의는 버전과 시각을 덮어쓰지 않는다.
- 노래방 · 커버곡 기능은 `karaoke_at > 0` 인 곡만 대상으로 해야 한다.
- 이용약관 6조에 조항 추가 (`/terms#karaoke`). 원곡을 비공개로 돌리면 반주 제공이 멈추고 커버곡도 함께 비공개가 된다.

## ② MR 자동 생성 (배포됨)

- 원곡 변환이 끝나면 노래방 조항에 동의한 곡은 MR 작업이 자동으로 대기열에 들어간다 (`karaoke_jobs`, 마이그레이션 `0009_karaoke_jobs.sql`).
- 가사 싱크 작업자(`alignment/`) 하나가 가사 작업 → 노래방 작업 순서로 **한 번에 한 곡씩** 처리한다. 사이그램 서버 부하를 CPU 2개 · 메모리 4GB 한도 안에 묶어 둔다.
- 순서: 보컬 분리(htdemucs) → MR · 보컬 파일 저장(R2 `karaoke/{track}/`) → 창작자 싱크 가사를 **분리된 보컬**에 맞춰 단어별 시간 저장.
- 창작자가 싱크 가사를 고치면 MR은 그대로 두고 단어 싱크만 다시 맞춘다. 원곡을 다시 변환하면 MR도 새로 만든다.
- 창작자는 스튜디오 곡 수정 화면에서 MR을 들어보고, 「자동으로 다시 만들기」 또는 「내 반주 파일로 바꾸기」(원곡과 길이 ±3초 이내 WAV · FLAC · MP3)를 할 수 있다.
- 10분 넘는 곡은 MR을 만들지 않는다.
- 기존 가사 자동 싱크도 분리된 보컬이 있으면 보컬 파일로 맞춘다.
- 로컬 측정: 2분 36초 곡 보컬 분리 86초, 단어 싱크 17초 (CPU 2스레드).
- 서버 측정 (운영과 같은 제한 · 인터넷 차단): 2분 36초 곡 분리 207초 · 단어 싱크 34초, 9분 55초 곡 분리 약 12분 · 최고 메모리 2.87GB (한도 4GB). 곡 길이의 약 1.2~1.3배 걸린다.

### 서버 작업자 배포 기록 (2026-09-24 01:30 KST)

- 서버 `/root/aifect`, compose 프로젝트 `aifect`, 파일 `compose.lyrics.yml`, 컨테이너 `aifect-lyrics-1` 만 교체했다. 같은 프로젝트에 `compose.yml`(변환) · `compose.billing.yml`(결제 중계)이 함께 있으므로 **`--remove-orphans` 를 쓰면 안 된다** — 다른 두 작업자가 지워진다.
- 이미지 `aifect-lyrics:latest` = `a18a776fe49a` (서버에서 실제 곡으로 분리 · 단어 싱크 · 기존 줄 단위 싱크를 시험한 이미지 그대로).
- 되돌리기용으로 이전 이미지 `aifect-lyrics:before-karaoke` (`867cd548b349`)와 이전 파일 `/root/aifect/alignment.bak-20260924` 를 남겼다. 한동안 문제가 없으면 지워도 된다 (약 5GB).
- 되돌리는 방법:

```sh
cd /root/aifect
rm -rf alignment && mv alignment.bak-20260924 alignment
docker tag aifect-lyrics:before-karaoke aifect-lyrics:latest
docker compose -p aifect -f compose.lyrics.yml up -d --no-build --force-recreate lyrics
```

- 작업자 오류는 `docker logs aifect-lyrics-1` 에 `karaoke_error` · `karaoke_words_error` 로 남고, 실패한 단계의 오류 출력 끝부분이 `detail` 에 붙는다.
- 노래방 대상 곡 조건: `karaoke_at > 0` · `karaoke_jobs.state='ready'` · `words_state IN ('ready','attention')` · 곡 공개 상태.

## ③ 커버곡 · 통합 프로필 (운영자 수정 요청, 2026-09-24)

- **한 계정, 하나의 공개 프로필**: 같은 이용자가 음악을 제작하고 노래방에서 커버도 부를 수 있다. 제작자/커버 가수 역할을 따로 선택하거나 별도 프로필을 만들게 하지 않는다. 기존 제작자 프로필을 통합 프로필로 확장하고, 커버만 올리는 이용자도 같은 구조를 사용한다.
- **공통 프로필 상단**: 대표 이미지(배너), 프로필 사진, 활동명, 소개, 팔로워는 한곳에서 관리하고 표시한다.
- **프로필 아래 콘텐츠 탭**: 「제작곡」과 「커버곡」으로 목록을 나눈다. 제작곡에는 직접 만든 원곡을, 커버곡에는 자신이 부른 곡과 원곡 정보를 표시한다. 두 탭에 모두 곡을 올릴 수 있고, 아직 곡이 없는 탭은 해당 종류의 곡이 없음을 안내한다.
- **사람과 콘텐츠 구분**: 제작곡/커버곡은 곡의 구분이다. 사람을 제작자/가수로 분리하지 않는다. AI 아티스트는 이용자의 역할과 다른, 제작곡에 연결된 기존 음악 캐릭터 프로필이다.
- **커버곡**: 원곡 페이지의 「커버곡」 탭과 부른 사람의 통합 프로필 내 「커버곡」 탭에 나온다. 원곡자와 커버한 사람을 각각 표시하고 각자의 통합 프로필로 연결한다. 커버곡마다 댓글 · 좋아요 · 선물이 가능하다.
- **순위**: 원곡별 커버곡 순위(좋아요 · 선물 · 재생). 커버곡별 순위와 이용자 통합 프로필의 **선물을 많이 준 사람 순위**(1등부터, 선물 개수 기준)를 보여준다. 개인 프로필을 활동 역할별로 나누지 않되, 원곡자/커버한 사람에 대한 정산 내역은 곡별 기여에 따라 구분한다.
- 선물 기능 자체(재화 구매 · 정산)는 ④에서 만든다. ③에서는 좋아요 · 댓글 · 순위 화면의 자리를 먼저 만든다.
- 구현 상태: 통합 프로필 탭과 커버곡 업로드는 아직 기획 단계다. 현재 운영 화면에 완료된 기능으로 표시하지 않는다.

## 수익 배분 (운영자 결정, 2026-09-24)

### 스트리밍 수익풀
- 스트리밍 수익의 **40%** 를 수익풀로 만든다.
- 매월 1일~말일 수익을 **곡별 스트리밍 수 비율**로 나눠, **다음 달 15일** 정산한다.
- **노래방 재생도 스트리밍 수에 포함**한다.
- 누적 **10,000원 이상**일 때 지급하고, 미만이면 다음 달로 이월한다.

### 선물
- 커버곡에 선물이 들어오면 **커버한 사람 40% · 원곡자 30% · 플랫폼 수수료 30%**.

## 정해야 할 것

1. **스트리밍 수익의 범위** — Premium 구독료만인지, 광고 수익도 포함인지. 부가세 · 결제 수수료를 뺀 금액 기준인지.
2. **스트리밍 수로 셀 재생** — 지금 차트와 같은 기준(30초 또는 곡의 60% 이상, 한 사람당 하루 1회)을 쓰면 부정 재생을 어느 정도 막을 수 있다.
3. **커버곡 재생의 몫** — 커버곡이 재생되면 커버한 사람 몫인지, 원곡자와 나누는지.
4. **노래방 재생의 몫** — 원곡자에게 가는 것으로 보이는데 확정 필요.
5. **원곡에 직접 받은 선물** — 커버가 아닌 원곡에 선물하면 원곡자 70% · 수수료 30% 인지.
6. **앱 인앱결제 수수료** — 앱에서 재화를 팔면 애플 · 구글이 15~30%를 먼저 가져간다. 앱 결제분에 선물 수수료 30%를 그대로 두면 플랫폼 몫이 거의 남지 않는다. 앱 결제분은 배분 기준을 따로 두거나, 재화 가격을 웹보다 높게 잡는 방식을 검토해야 한다.
7. **정산 방식** — 개인 창작자 지급 시 원천징수(사업소득 3.3% 등), 계좌 인증, 본인 확인 절차.

위 배분 기준은 ③ · ④ 구현 때 이용약관과 창작자 정산 안내에 반영한다. 현재 약관은 "업로드만으로 정산이나 수익 배분이 약속되지 않는다"는 문구를 유지한다.
