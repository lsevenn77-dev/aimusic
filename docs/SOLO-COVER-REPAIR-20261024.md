# 두 솔로 커버 분류 정정

## 확인한 문제

2026-10-24 공개 API에서 아래 두 커버가 `cover_mode=duet`, `duet_open=1`, `duet_parent_id=null`로 조회됐다. 운영자는 두 녹음이 솔로 커버임을 확인했다.

| 작품 | 커버 ID | 원곡 ID |
| --- | --- | --- |
| 별일 아닌 것처럼 | e8ce3d21-43f4-4eee-bf8c-e6187b417d7d | d4c239cc-d765-4ca3-a62e-97283a7c9e8b |
| 비행운 | 40d9c296-8098-4f3a-a4d5-344a3621d60f | 2b4a4bce-a7e9-4f80-b688-d49b551c0cef |

`/api/duets`는 공개된 모집 중 듀엣을 반환하고 `/api/play/works`는 솔로 커버·완성 듀엣·완성 더빙을 반환한다. 두 곡만 있는 현재 커버 목록에서 위 데이터 때문에 앱의 둘러보기가 비었다. 원곡의 `performance_mode`는 커버 녹음 방식과 다르며, 이를 근거로 다른 커버를 자동 재분류하면 안 된다.

현재 웹·Android의 업로드 경로는 사용자가 선택한 `cover_mode`를 전송한다. 서버 기본값은 solo이며 새 듀엣에는 별도 참여 동의가 필요하다. 과거 두 업로드가 duet로 제출된 구체적 경위는 공개 데이터만으로 확인되지 않았다.

## 수정 범위

`0076_repair_confirmed_solo_covers.sql`은 위 두 ID와 각 원곡, 소유자, 프로필이 모두 일치하는 공개 듀엣 모집 원본만 정정한다. 참여한 자식 녹음이 하나라도 있으면 삭제 상태를 포함해 정정을 건너뛴다. 실제 듀엣이나 다른 사람의 작품을 변경하지 않는다.

- `cover_mode=solo`, `duet_open=0`, `duet_part=''`, `duet_guide=''`.
- 음원 ID·파일·R2·소유자·게시 시각·재생/좋아요/댓글·결제/정산·XP는 유지한다.
- 같은 UPDATE 문 안에서 기존 `admin_audit`에 이전/이후 분류를 남긴다. 감사 저장이 실패하면 분류 변경도 실패한다.
- 분류 정정이 새 공개 이벤트로 인식되어 봇 댓글/선물을 생성하지 않도록 기존 공개 이벤트 트리거 조건을 보완한다. 실제 신규 공개 및 듀엣 완성 이벤트는 유지한다.
- 추가되는 영구 테이블·열은 없다. 감사용 임시 운영 트리거는 해당 migration 마지막에 제거된다.
- Android 화면·로고·녹음 방식·웹 디자인은 수정하지 않는다. 배포 후 기존 앱이 목록을 새로 조회하면 정정 결과를 받는다.

## 검증 및 게시

`tests/solo-cover-repair.test.mjs`에서 실제와 동일한 두 분류 상태를 로컬 SQLite로 재현하고 목록 API, 파일 정보/XP 보존, 중복 적용, 실제 참여자 보호, 감사 실패 원자성, 봇 신규 공개 이벤트를 검증한다. 과거 XP migration을 의도적으로 뒤늦게 적용하는 테스트 fixture도 의존 순서를 맞춘다.

전체 테스트와 빌드는 `npm run release:prepare`로 실행하고 결과는 `work/releases/latest.json`에서 확인한다. 공식 Sites에 후보만 저장한 뒤 새 버전의 배포 및 이 두 운영 데이터 정정 승인을 함께 요청한다. 승인 전에는 운영 DB를 변경하지 않는다.

게시 후 `/api/community?kind=cover&cover_mode=solo`, `/api/play/works?tab=latest&type=solo`, `/api/duets`, 원곡별 `/api/tracks/:id/covers?mode=solo`에서 두 ID를 확인한다. guarded update가 건너뛴 항목은 조건을 재조회하고 재분류하지 않는다. 실제 앱의 둘러보기와 듀엣 목록도 확인한다.

## 복구

코드 버전을 되돌려도 데이터 migration은 자동으로 취소되지 않는다. 복구가 필요하면 `admin_audit`의 `repair-0076:<커버 ID>`에 저장된 이전 네 필드를 검토한다. 현재 분류·추가 참여·이후 편집을 확인하고 별도 승인된 새 migration으로 복구와 추가 감사 기록을 남긴다. 기존 감사 기록이나 음원 파일은 삭제하지 않는다.
