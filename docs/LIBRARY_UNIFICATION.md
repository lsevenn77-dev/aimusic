# 마이박스 이전과 검증

운영 DB는 기존 AIFECT Sites 프로젝트의 `DB` 바인딩입니다. 별도 음성룸 DB에는 다른 데이터가 있습니다.

## 백업과 영향 확인

1. 운영 DB 관리 도구에서 전체 스키마와 데이터가 포함된 일관된 백업을 내보내고 접근이 제한된 저장소에 보관합니다. 사이트 소스 아카이브에는 운영 DB가 포함되지 않습니다.
2. 전체 백업을 별도의 SQLite 파일에 복원하고 연결을 종료합니다. `node scripts/verify-library-backup.mjs <복원본.sqlite>`을 실행합니다. 이 명령은 기존 배포 스키마의 테이블 존재 여부, SQLite 무결성, 외래 키, 마이박스와 항목의 내용, 열 순서가 고정된 해시, 복원 파일의 SHA-256을 점검합니다. 출력에는 개별 사용자 데이터가 없습니다.
3. 같은 백업을 기준으로 후보 버전을 격리된 환경에서 검증합니다. 마이박스가 없더라도 내용 대조를 실행해야 세 개 탭이 활성화됩니다. 확인한 백업과 로컬 검증 결과를 보관한 뒤 DDL과 후보 Worker를 기존 운영 프로젝트에 적용할 수 있습니다. DDL은 새 테이블과 뷰를 추가합니다.
4. 기존 관리자 콘솔 세션으로 `GET /api/admin/library-unification`을 조회합니다. 백업 검증 결과와 건수 및 원본 해시를 대조합니다. 조회 결과의 충돌 목록은 관리자만 볼 수 있습니다.

## 충돌 처리

같은 제목의 목록도 각자의 ID와 제목을 유지한 채 이전합니다. 대상 플레이리스트 ID가 이미 있는 경우 충돌 목록에 마이박스 ID를 표시합니다. 해당 ID의 충돌을 해결한 뒤 백업과 점검을 다시 실행합니다.

## 이전과 재시도

검증한 백업 명령의 JSON 출력을 같은 관리자 콘솔 세션에서 `POST /api/admin/library-unification`의 본문으로 보냅니다. 서버가 트랜잭션 안에서 마이박스 원본을 다시 대조합니다. 소유자, 제목, 비공개 상태, 생성·수정 시각 및 모든 항목의 종류·ID·순서·등록 시각을 양방향으로 검증하고 나서 완료 기록을 씁니다. 콘텐츠 본체가 없어도 항목 참조를 보존합니다. 원본 마이박스 테이블과 백업은 유지됩니다.

입력 변경이나 ID 충돌, 복사 오류가 발생하면 D1이 해당 트랜잭션을 롤백합니다. 변경 뒤에는 새 전체 백업을 검증하여 재시도합니다. 완료 뒤 재요청하면 최초 검증 결과를 반환합니다. 조회용 `GET /api/library/unification`은 완료 여부만 돌려주며, 클라이언트가 같은 결과로 보관함과 콘텐츠 추가 메뉴를 전환합니다.

검증 후 생성된 플레이리스트에는 신규 편집이 쌓일 수 있습니다. 복구 시에는 검증 시점 이후의 쓰기 내역과 원본 백업을 함께 확인해야 합니다.

## 삭제가 승인된 경우

마이박스와 수록 참조 전체의 삭제가 승인되면 두 원본 테이블을 함께 내보내고 별도 환경에서 복원을 확인합니다. 복원본의 건수와 원본 SHA-256을 비교합니다. 배포 전 Sites 운영 설정 `AIFECT_MY_BOX_RETIREMENT`에 검증한 `source_sha256`, `backup_sha256`, `boxes`, `items`를 JSON으로 등록합니다. 배포가 끝나면 인증된 작업 서버가 다음 요청에서 이 설정을 확인합니다. 적용 결과를 확인한 뒤 운영 설정에서 해당 값을 제거합니다.

서버는 적용 직전에 같은 데이터를 다시 대조합니다. 마이박스 목록과 수록 참조를 비우고 두 테이블이 모두 비었음을 확인한 뒤 통합 보관함을 활성화합니다. 삭제 결과는 같은 트랜잭션에서 감사 기록에 남습니다. 기존 제작곡, 커버곡, 더빙, 플레이리스트, 북마크는 보존합니다. 삭제 이전의 마이박스 링크는 통합 보관함의 플레이리스트 탭으로 이동합니다.
